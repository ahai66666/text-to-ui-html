# Stage resource queries
RULES_ROOT is this skill directory. Run query-resources.mjs with --stage, --view api and optional --out-dir outside the skill. Read task-pack.json OR task-pack.md, not both. read-plan.json is provenance/measurement metadata. Full indexes, component aggregates and source code are machine inputs.
Stages: intake → design → discovery → bindings → styling → validation. Resolve-context produces a machine packet and a v2 navigation brief. API queries use --component <exact-id> --semantic-context <context>, or --bindings <file>; Token queries use --roles. Execute the new-page, normalize-demo or micro-revision workflow appropriate to the task. Source validation, build, browser and visual results remain distinct. After acceptance, page:handoff prepares the independent Pixso handoff.
Commands: resources:build → catalog:build → index:build, then corresponding checks and skill:manifest. Unknown IDs, ambiguity, stale sources and missing dependencies stop the query. --max-bytes rejects over-budget output without truncating rules. JSON UTF-8 byte counts are not Token counts. Other models receive only the current pack and confirmed decisions; a new conversation does not inherit the previous chat automatically.

Workflow policy is maintained in references/routes/index.json. Always retain --workflow in the next query; conflicting workflow/context selectors are rejected. new-page and normalize-demo use six stages; micro-revision uses intake/bindings/styling/validation and inherits Task/Pattern; skill-maintenance uses intake/validation without a page context. Skip unaffected stages only when required inputs remain valid.
Carry --blueprint, --bindings and --preservation paths as available. A next-query command preserves supplied selectors; the machine Context Packet refreshes source hashes, while actual browser acceptance must always be fresh. Each pack lists its completion conditions and workflow-specific commands. For a fresh model, supply the brief, current pack, confirmed decisions and any preservation/shared-rule inputs explicitly.
--scope component projects a smaller bindings API pack; omitted shared-rule references must already be in the model context. Default complete is self-contained with its required resource closure. --max-bytes rejects oversized packs rather than silently removing rules. The HTML workflow terminates after accepted handoff creation; it cannot enter an import phase.

Component API packets expose `implementation.sourcePath` / `exportName` and `projectModule` without loading JS bodies. Exact component IDs take priority over broad aliases in every lookup; semantic contexts still disambiguate roles.
Titlebar sources use maintained `tui-scope` markers. Task packets project only matching semantic/known A/B Pattern sections; unknown selectors and C/D bases retain unproven sections. `--view full` or an explicit resource ID returns all rules. Compatibility manuals strip markers and retain every section. `read-plan.json.resourceProjections` records selectors and byte counts. Multi-binding queries retain the union of required contexts. Short packets omit only rules that actually exist in the generic bindings packet; component-only prerequisites remain included.

For primary-navigation Titlebar API queries, inactive slots are listed in apiProjection.inactiveSlots while only applicable slot contracts are included; --view full returns the original complete contract. This narrows documentation only, not component rendering or compiler validation.
